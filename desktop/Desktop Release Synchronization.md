## 1. What Is a "Release"?

A single "release" in this codebase produces three distinct artifacts:

| Artifact | Identity Source | Delivery Mechanism |
|---|---|---|
| **Web dist/** | `BUILD_ID` (git short SHA) + `COMMIT_HASH` | GitHub Pages CDN |
| **build-manifest.json** | Generated by Vite plugin at build time | Same GitHub Pages CDN |
| **Electron EXE** | `package.json` version (e.g. `1.4.0`) | GitHub Releases (NSIS installer) |

**Key insight:** The Web dist and the manifest are the *same* deploy. The manifest is generated inside the build and uploaded alongside `index.html` and `assets/`. The EXE is a separate build from the same commit.

## 2. The Three Concerns

The Desktop application synchronizes with the Web release through three independent concerns:

### Concern 1: Data Sync (Remote Supabase → Local Postgres)
- **What:** Business data (orders, products, customers, employees, etc.)
- **When:** Every startup + periodic via ConnectivityMonitor
- **Engine:** `InitialSync.ts` → `pg` direct connection to local Postgres, HTTP to Supabase REST
- **IPC:** `db:initial-sync`, `db:incremental-sync`
- **Untouched by auto-update system**

### Concern 2: Schema Migration (Remote GitHub → Local Postgres)
- **What:** SQL DDL that evolves the local database schema
- **When:** Every startup (bundled) + on-demand (remote)
- **Engine 1:** `SchemaMigrator.ts` — reads from `resources/migrations/` (bundled with EXE)
- **Engine 2:** `MigrationUpdater.ts` — downloads from GitHub API at runtime
- **IPC:** None directly (runs at startup before window creation)

### Concern 3: Application Auto-Update (GitHub Pages → Renderer Cache)
- **What:** JavaScript, CSS, HTML (the renderer/frontend)
- **When:** At startup with retry loop
- **Engine:** `UpdateCoordinator.ts` + `RendererUpdater.ts`
- **IPC:** `update:full-cycle`, `update:activate-renderer`, `update:restart`
- **Source of truth:** `build-manifest.json` on GitHub Pages

## 4. Release Manifest Contract

### Format (`build-manifest.json`)

```json
{
  "build_id": "b999731",              // git short SHA
  "commit_hash": "b999731...",        // full git SHA
  "build_date": "2026-08-17T...",     // ISO timestamp
  "app_version": "1.0.0",             // from VITE_APP_VERSION env
  "required_schema_version": 7,       // from migrations/manifest.json
  "assets": {
    "index-[hash].js": "sha256:abc...",
    "index-[hash].css": "sha256:def...",
    ...                               // one entry per file in assets/
  }
}
```

### Where It's Fetched From

```
https://ahram-distribution.github.io/store/build-manifest.json
```

Defined at `ReleaseManifest.ts:20` as `MANIFEST_URL`.

### What the Desktop Checks

`compareManifests()` at `ReleaseManifest.ts:38-58` compares:

| Field | Comparison | Meaning |
|---|---|---|
| `build_id` vs `appliedBuildId` | String equality | Renderer changed? |
| `required_schema_version` vs local | Integer greater-than | Schema upgrade needed? |
| `app_version` vs `app.getVersion()` | Semver greater-than | EXE upgrade needed? |

All three must be equal/lesser for `isCurrent = true`.

## 9. Concern 1: Data Sync

### Components
- `InitialSync.ts` — table-by-table sync from Supabase REST to local Postgres
- `ConnectivityMonitor.ts` — periodic incremental sync trigger

### Tables Synced (from `SYNC_TABLES` in InitialSync.ts)
- identities, employees, roles, capabilities
- employee_roles, role_capabilities, employee_capabilities
- customers, customer_addresses, customer_contacts, customer_credit_accounts
- products, product_units, companies
- orders, order_items, order_status_history, order_modification_history
- ... (30+ tables)

### Sync Protocol
1. On startup: full initial sync if `sync_requires_full_refresh` flag is set, otherwise incremental
2. Periodic: ConnectivityMonitor triggers `incrementalSync` on network state change
3. All sync goes through `desktopSupabase.rpc()` → `window.api.db.query()` → LOCAL Postgres
4. The renderer NEVER talks to remote Supabase directly for data

### Quarantine System
- Conflicting records are quarantined, not dropped
- `getSyncQuarantineStatus()` returns pending conflicts and quarantined tables
- OFFLINE_READY is only granted when quarantine is empty

## 10. Concern 2: Schema/Migration Update

### Two Engines, Two Sources

| | Bundled (SchemaMigrator) | Remote (MigrationUpdater) |
|---|---|---|
| **Source** | `resources/migrations/` (inside EXE) | GitHub API |
| **When** | Every startup | Auto-update cycle |
| **Format** | Files on disk | HTTP fetch → cache to disk |
| **Transactional** | Yes (per-migration BEGIN/COMMIT/ROLLBACK) | Yes (per-migration BEGIN/COMMIT/ROLLBACK) |
| **Failure** | App refuses to start | Returns false, triggers retry |

### SchemaMigrator Flow (Startup)

```
getSchemaState()
  ├── Read manifest.json (bundled)
  ├── Query schema_migrations table
  ├── Detect: fresh DB, existing data, or migration needed
  └── Return: { currentVersion, pendingMigrations, requiredVersion }

migrateSchema()
  ├── IF no schema_migrations table:
  │   ├── Create it
  │   ├── IF DB has data → adopt baseline (record without re-running)
  │   └── IF fresh DB → apply schema.sql + record baseline
  ├── For each pending migration:
  │   ├── BEGIN
  │   ├── INSERT INTO schema_migrations (version, status='applied')
  │   ├── Execute migration SQL
  │   ├── COMMIT
  │   └── ON FAILURE: ROLLBACK + INSERT status='failed' + return error
  └── Return: { success, applied[], failed? }
```

### MigrationUpdater Flow (Auto-Update)

```
fetchRemoteMigrationsManifest()
  └── GET GitHub API: /contents/desktop/main/db/migrations/manifest.json
      └── Parse JSON, return migrations[]

downloadMigrationFiles()
  ├── Filter: version > localSchemaVersion
  ├── For each: fetch via GitHub API (base64 or download_url fallback)
  ├── Cache to: %APPDATA%/ahram-desktop/ahram-desktop/remote-migrations/
  └── Return downloaded[]

applyRemoteMigrations()
  ├── Connect to local Postgres
  ├── Query current version from schema_migrations
  ├── For each pending:
  │   ├── BEGIN
  │   ├── INSERT INTO schema_migrations
  │   ├── Execute SQL
  │   ├── COMMIT
  │   └── ON FAILURE: ROLLBACK + INSERT failed + return error
  └── Return: { applied, failed }
```

### GitHub API Path

```
GET https://api.github.com/repos/ahram-distribution/store/contents/desktop/main/db/migrations/manifest.json
GET https://api.github.com/repos/ahram-distribution/store/contents/desktop/main/db/migrations/{file}
```

For files under 1MB, GitHub returns inline base64. For files over 1MB (e.g. `0006_web_parity_roundtrip.sql`), it returns a `download_url` to `raw.githubusercontent.com`.

## 11. Concern 3: Application Auto-Update

### Source of Truth

```
https://ahram-distribution.github.io/store/build-manifest.json
```

### Architecture

```
UpdateCoordinator.checkForUpdates()
  ├── Fetch remote manifest
  ├── Compare with local state
  ├── IF isCurrent → done
  ├── IF appNeedsUpgrade → restart-required (EXE needed)
  ├── IF isRetryBlocked → retrying (exponential backoff)
  ├── IF rendererChanged → downloadNewRenderer()
  │   ├── Check isRendererCached()
  │   ├── Download from GitHub Pages (assets + index.html + build-manifest.json)
  │   ├── Verify SHA-256 for each asset
  │   ├── Save to: renderer-cache/{buildId}/
  │   └── Write pendingRendererBuildId to state
  ├── IF schemaNeedsUpgrade → downloadAndApplyMigrations()
  │   ├── Fetch remote manifest via GitHub API
  │   ├── Download migration SQL files
  │   └── Apply with transactional safety
  ├── IF both succeeded → restart-required
  └── IF either failed → retrying (increment retry count)
```

### Renderer Download Details

From `RendererUpdater.ts`:

1. **Extra files** (fetched from `BASE_URL`):
   - `index.html`
   - `build-manifest.json`

2. **Asset files** (fetched from `ASSETS_URL`):
   - Every entry in `manifest.assets` (the `dist/assets/` files)
   - Each verified against SHA-256 hash from manifest
   - Downloaded in parallel batches of 4

3. **Target directory**: `renderer-cache/{buildId}/`

4. **Manifest snapshot**: `_manifest.json` written to cache dir

## 14. The Retry Loop

From `main.ts:227-244`:

```typescript
const runUpdateWithRetry = async () => {
  const info = await performFullUpdateCycle(dbConfigForUpdate)
  if (info.status === 'retrying') {
    const state = loadUpdateState()
    if (state.nextRetryAt) {
      const delayMs = Math.max(new Date(state.nextRetryAt).getTime() - Date.now(), 5000)
      setTimeout(runUpdateWithRetry, delayMs)
    }
  }
}
runUpdateWithRetry()
```

### Exponential Backoff (UpdateState.ts:81-86)

```
retry 1: 5s delay
retry 2: 10s delay
retry 3: 20s delay
retry 4: 40s delay
retry 5: 80s delay
retry 6: 160s delay
retry 7: 320s delay (5m 20s)
retry 8: 640s delay (10m 40s)
...
retry 11+: 1800s delay (30m, capped)
```

### Reset Conditions
- `isCurrent` → `clearRetryState()` resets retryCount to 0
- `rendererOk && migrationsOk` → `clearRetryState()` resets retryCount to 0

### Block Condition
`isRetryBlocked(state)` returns `true` if `Date.now() < nextRetryAt`, preventing immediate re-check.

## 15. Atomicity Guarantees

### Migration Apply (SchemaMigrator + MigrationUpdater)

Both engines use the same pattern:

```sql
BEGIN
  INSERT INTO schema_migrations (version, status='applied') VALUES (...)
  -- execute migration DDL
COMMIT
-- ON FAILURE:
ROLLBACK
INSERT INTO schema_migrations (version, status='failed', error_message=...)
```

**Guarantee:** Either the entire migration applies or nothing changes. The `schema_migrations` row is committed atomically with the DDL.

### Renderer Download (RendererUpdater)

**NOT atomic.** Downloads happen file-by-file:
1. Each asset is downloaded individually
2. SHA-256 verified before write
3. Failed downloads throw (file is deleted if partially written)
4. `isRendererCached()` checks for `index.html` existence
5. `pendingRendererBuildId` written only after all downloads succeed

**Risk:** If the app crashes mid-download, partially-downloaded files remain in the cache dir. However, `isRendererCached()` requires `index.html` to exist, so a partial download won't be mistakenly activated.

### Renderer Activation

**NOT atomic.** Two files are written:
1. `renderer-active-build` marker file
2. `update-state.json`

If crash occurs between these writes, the state file may reference an activated build that the marker doesn't point to, or vice versa. Recovery: the next startup reads `renderer-active-build` and verifies `isRendererCached()`.

## 16. Crash/Power Loss Analysis

### Scenario: Crash During Renderer Download

| State | Next Startup Behavior |
|---|---|
| No files downloaded | `isRendererCached()` → false, nothing activated |
| Some assets downloaded | `isRendererCached()` → false (no index.html) |
| index.html downloaded, not all assets | `isRendererCached()` → true! **Bug risk:** partial asset set could be served |
| All assets + index.html downloaded | `isRendererCached()` → true, pendingRendererBuildId set |
| pendingRendererBuildId written | `activatePendingRenderer()` runs, activates the build |

### Scenario: Crash During Migration Apply

| State | Next Startup Behavior |
|---|---|
| Before BEGIN | Migration not recorded, will retry |
| During DDL execution | ROLLBACK undoes everything, status='failed' recorded |
| After COMMIT | Migration applied, next startup skips it |

### Scenario: Crash During Activation

| State | Next Startup Behavior |
|---|---|
| marker written, state not updated | State still has pendingRendererBuildId, activation re-runs |
| State updated, marker not written | `getActiveRendererPath()` returns null, bundled dist used |

### Scenario: Crash During State Write

| State | Next Startup Behavior |
|---|---|
| Corrupted JSON | `loadUpdateState()` catches, returns `defaultState()` |
| Half-written JSON | Same as corrupted (readFileSync may throw) |

## 17. Rollback Capability

### Renderer Rollback: **NONE**

There is no mechanism to roll back a renderer update. Once `renderer-active-build` points to a build, that build is served. The only recovery paths are:
1. Manually delete the `renderer-active-build` marker file
2. Reinstall the application

### Migration Rollback: **PARTIAL**

Each migration runs in a transaction. If it fails, ROLLBACK undoes the SQL. The `schema_migrations` row is recorded as `status='failed'`. However:
- There's no mechanism to undo a successfully-applied migration
- The `schema_migrations` table records both applied and failed migrations
- If a migration applies but causes runtime errors, there's no automatic rollback

### State Rollback: **NONE**

If the state file records a wrong `appliedBuildId`, there's no mechanism to correct it automatically.

## 19. Preload Contract Surface

The preload script (`preload/index.ts`) is the **only** bridge between renderer and main. The renderer has no direct access to:
- Node.js APIs
- File system
- PostgreSQL
- Network (except what the browser provides)
- Electron APIs

Every privileged operation goes through `ipcRenderer.invoke()`.

**The IPC contract is FIXED at EXE build time.** If the Web release adds a new IPC channel that the preload doesn't expose, that feature silently fails. This is why preload changes require EXE replacement.

## 24. Post-Migration Parity Gate

After a bundled migration applies (`main.ts:71-90`):

1. Delete `offline_ready` from `app.app_settings`
2. Insert `sync_requires_full_refresh = true`
3. This forces a fresh initial sync on the next startup
4. After sync converges (no quarantined records), `offline_ready` is set again

**Purpose:** A schema migration may have added new columns/tables that need data from Supabase. The old sync state can't be trusted to prove parity.

## 28. Security Model

### Renderer Integrity
- Each asset is verified against SHA-256 hash from `build-manifest.json`
- Hash mismatch → download fails, file is deleted
- The manifest itself is fetched over HTTPS from GitHub Pages

### No Code Signing
From `electron-builder.yml:65-66`:
```yaml
sign: false
signAndEditExecutable: false
```
The EXE is unsigned. Windows SmartScreen may warn on first run.

### No ASAR Integrity Check
The ASAR is not signed or integrity-checked. If an attacker can modify the ASAR, they can execute arbitrary code in the main process.

### Database Credentials
From `supabase.ts`, credentials are loaded from:
1. `process.env` (set by CI)
2. `.env.local` file
3. Bundled `resources/supabase.json`

The `supabase.json` is shipped with the installer and contains the Supabase URL and anon key.

### Migration Download Security
Migrations are fetched from GitHub's API without integrity verification beyond HTTPS. There's no signature check on the SQL files. A compromised GitHub account could inject malicious SQL.

## 32. Known Issues and Limitations

### Critical
1. **No renderer rollback** — If a bad renderer is activated, there's no way to go back without manual intervention
2. **No ASAR integrity check** — Main process code can be tampered with
3. **No migration signature verification** — Remote SQL is trusted without cryptographic verification
4. **Partial download can pass isRendererCached()** — If `index.html` is downloaded but some assets are missing, the check passes

### Moderate
5. **No EXE auto-update via custom system** — The `electron-updater` integration exists but the custom system only handles renderer + migrations
6. **ipcRenderer.on listeners are never cleaned up** — Memory leak on repeated listener registration (preload listeners persist for app lifetime)
7. **No download resume** — Partial downloads are restarted from scratch
8. **Migration timeout may be too short** — 15s for large SQL files via GitHub API

### Minor
9. **Double-nested path** — `%APPDATA%/ahram-desktop/ahram-desktop/` (§31)
10. **renderer-pending directory** — Created but no longer used as download target
11. **Legacy electron-updater still registered** — May conflict with custom system

## 37. EXE Update Boundary

> **Status:** VERIFIED

### Case Analysis

#### Case 1: Renderer Only (React component, CSS, page, navigation, UI behavior)

1. **Can current Desktop update automatically?** YES — `UpdateCoordinator` detects `build_id` change, downloads renderer assets, activates on restart.
2. **EXE update required?** NO.
3. **Restart required?** YES — renderer is served from a file cache, must restart to swap the active directory.
4. **Can electron-updater handle it?** Not needed — the custom system handles it.
5. **User action?** Click "Restart Now" when prompted.

#### Case 2: Renderer + Database (new screen + new table + migration + RPC)

1. **Can current Desktop update automatically?** PARTIALLY — renderer yes, migrations yes (if committed to `desktop/main/db/migrations/`), but new RPCs must exist in the SQL files BEFORE the renderer tries to call them.
2. **Critical ordering constraint:** The migration must apply BEFORE the new renderer tries to call the new RPC. Currently both happen in the same `checkForUpdates()` cycle, and migrations are applied before renderer activation.
3. **EXE update required?** NO — IF the migration is committed to the repo and the `build-manifest.json` includes the new `required_schema_version`.
4. **Risk:** If the new RPC is only defined on remote Supabase but not in any desktop migration file, the desktop app will have the new renderer (calling the new RPC) but no local definition of that RPC. **This is the current gap** — 2 RPCs are missing.

#### Case 3: Main Process Change (`desktop/main/main.ts`)

1. **Can current Desktop update automatically?** NO.
2. **Why?** Main process code is packed in the ASAR archive, which is read-only at runtime.
3. **Required mechanism?** New EXE build + NSIS installer + manual or electron-updater distribution.
4. **Can this mechanism be automatic?** YES — electron-updater is configured but not integrated into the custom system. It could download + install the new EXE automatically.
5. **Does the user need to reinstall manually?** Currently YES (electron-updater is not connected). Could be NO if integrated.
6. **Does the EXE updater need to be in the same Release Synchronization system?** YES — see §40.

#### Case 4: Preload Change (`desktop/preload/index.ts`)

1. **Can current Desktop update automatically?** NO.
2. **Why?** Preload is in the ASAR. It defines the IPC contract between renderer and main. A new preload + old main or old preload + new renderer = broken IPC.
3. **Required mechanism?** Same as Case 3 — new EXE.
4. **Automatic?** Same as Case 3.

#### Case 5: IPC Change (new channel, modified contract)

1. **Can current Desktop update automatically?** NO.
2. **Why?** New IPC channels require changes in three places: preload (`ipcRenderer.invoke`), main handler (`ipcMain.handle`), and renderer caller. The preload and main handler are in the ASAR.
3. **The renderer CAN be updated** (it's the caller), but the other two endpoints cannot.
4. **Result:** If the renderer calls a new IPC channel that the old preload doesn't expose, the call silently returns `undefined`. The feature fails silently.

#### Case 6: Native Dependency (pg, Electron dependency)

1. **Can current Desktop update automatically?** NO.
2. **Why?** Native modules contain platform-specific binaries that must match the Electron version and Node.js ABI.
3. **Required mechanism?** New EXE build with updated `node_modules`.

#### Case 7: Electron Runtime/Version

1. **Can current Desktop update automatically?** NO.
2. **Why?** Electron is the application shell. It can't replace itself.
3. **Required mechanism?** New EXE build with new Electron version.
4. **electron-updater can handle this** — it downloads and installs the new NSIS package.

### Boundary Summary

```
CAN auto-update:                          CANNOT auto-update (need EXE):
├── Renderer JS/CSS/HTML                  ├── Main process code
├── Database schema migrations            ├── Preload script
├── Database RPC definitions*             ├── IPC handlers
├── Database views/triggers*              ├── Native modules (pg)
```

## 38. Release Identity Decision

> **Status:** PROPOSED

### Current Identity Fields

| Field | Source | Scope | Sufficient? |
|---|---|---|---|
| `build_id` | Git short SHA | Renderer build identity | Partial — renderer only |
| `commit_hash` | Full Git SHA | Source code identity | Yes — uniquely identifies the code |
| `app_version` | `package.json` version | EXE/ASAR identity | Partial — EXE only |
| `required_schema_version` | `migrations/manifest.json` | Database schema level | Partial — version number only |

### The Question

> "Which project Release am I currently running?"

The Desktop cannot answer this with one field. It has:
- `appliedBuildId` — which renderer build is active
- `app.getVersion()` — which EXE version is installed
- `schema_migrations.max(version)` — which schema version is applied
- No knowledge of which *commit* all three correspond to

### Proposed: Unified Release Contract

```json
{
  "release_id": "<commit_hash>",
  "renderer_build_id": "<build_id or null>",
  "app_version": "<semver>",
  "schema_version": "<integer>",
  "renderer_compatibility": {
    "min_app_version": "<semver>",
    "min_schema_version": "<integer>"
  },
  "app_compatibility": {
    "min_renderer_build_id": "<build_id or null>",
    "min_schema_version": "<integer>"
  }
}
```

**Key addition:** `renderer_compatibility` and `app_compatibility` blocks that declare prerequisites. This prevents:
- New renderer running on old schema (renderer needs new RPC)
- Old renderer running on new schema (renderer doesn't know about new columns)

### Why commit_hash is the Release ID

`commit_hash` is the only field that:
1. Is unique per code change
2. Identifies the exact state of ALL components (renderer, main, preload, migrations)
3. Is already generated by CI
4. Can be verified against the git repository

`build_id` (short SHA) is equivalent but less collision-resistant. `app_version` only changes when `package.json` is bumped.

## 39. Release Compatibility Matrix

> **Status:** VERIFIED against current codebase

| Published Release Change | Desktop Action | Restart Required? | EXE Update Required? | DB Migration Required? | Rollback Required? |
|---|---|---|---|---|---|
| Renderer only (JS/CSS) | Download renderer assets | YES | NO | NO | NO (forward only) |
| CSS only | Download renderer assets | YES | NO | NO | NO |
| New page (lazy chunk) | Download renderer assets | YES | NO | NO | NO |
| New image in `public/` | **NOT auto-updated** (serves from bundled) | NO | NO | NO | NO |
| Renderer + DB migration | Download renderer + apply migration | YES | NO | YES | NO (migration is transactional) |
| Renderer + new RPC (in migration) | Download renderer + apply migration | YES | NO | YES (must define RPC) | NO |
| Renderer + new RPC (NOT in migration) | **PARTIAL** — renderer downloads, RPC missing at runtime | YES | NO | YES (but missing!) | NO |
| RPC signature change | Migration replaces function body | YES | NO | YES | NO |
| Main Process change | **NOT auto-updated** | YES | YES | NO | N/A |
| Preload change | **NOT auto-updated** | YES | YES | NO | N/A |
| IPC channel addition | **NOT auto-updated** (silent failure) | YES | YES | NO | N/A |
| Native dependency | **NOT auto-updated** | YES | YES | NO | N/A |
| Electron version | **NOT auto-updated** | YES | YES | NO | N/A |
| Full release (all components) | All of the above | YES | YES (if main/preload changed) | YES (if schema changed) | NO |

### Critical Compatibility Rule

> **INVARIANT:** The new renderer must NEVER be activated before the new schema migration has been applied.

Currently enforced by `UpdateCoordinator`:
1. `downloadAndApplyMigrations()` runs first
2. `downloadNewRenderer()` runs second
3. Both must succeed before `restart-required` is returned
4. `activatePendingRenderer()` runs at the NEXT startup, after migration has already been applied at the PREVIOUS startup

This ordering is correct and safe.

### Reverse Compatibility Rule

> **INVARIANT:** The new schema must NEVER break the old renderer.

Migrations that change RPC signatures (replacing function bodies) are backward compatible IF:
- The new function accepts all the same parameters
- The new function returns the same shape
- The old renderer's existing calls still work

Migration 0006 (503 function replacements) and 0007 (5 function replacements) follow this rule — they replace function bodies without changing signatures.

## 40. Dual Update Path Architecture

> **Status:** PROPOSED

### Current State: Two Independent Systems

```
                    PUBLISHED RELEASE
                           │
              ┌────────────┴────────────┐
              │                         │
     Custom UpdateCoordinator      electron-updater
     (Renderer + Migrations)       (EXE replacement)
              │                         │
     GitHub Pages manifest         GitHub Releases
     GitHub Contents API           NSIS installer
              │                         │
              └────────────┬────────────┘
                           ↓
                     SAME RELEASE
```

**Problem:** These systems are NOT coordinated. They share IPC channels (`update:status`) and can produce conflicting state. Neither system knows about the other's actions.

### Proposed: Unified Release Coordinator

```
                    PUBLISHED RELEASE
                           │
                    RELEASE MANIFEST
                    (commit_hash + version matrix)
                           │
                 ┌─────────┴─────────┐
                 │                   │
          RELEASE COORDINATOR    (new component)
                 │
    ┌────────────┼────────────┐
    │            │            │
 RENDERER    MIGRATION     EXE
 UPDATER     UPDATER       UPDATER
    │            │            │
 GitHub Pages  GitHub API   GitHub Releases
    │            │            │
    └────────────┼────────────┘
                 │
          HEALTH CHECK
                 │
          ┌──────┴──────┐
          │             │
       CONFIRMED    ROLLBACK
```

### What the Unified Coordinator Does

1. **Single entry point** — `performFullReleaseCycle()` replaces `performFullUpdateCycle()`
2. **Single manifest** — one release manifest contains all version information
3. **Ordered execution:**
   - Phase 1: Check manifest → determine what changed
   - Phase 2: Apply DB migrations (if needed)
   - Phase 3: Download renderer (if needed)
   - Phase 4: Download EXE (if needed, via electron-updater)
   - Phase 5: Health check
   - Phase 6: Activate (renderer pointer + schedule EXE install)
4. **Single notification channel** — no IPC conflicts
5. **Single state file** — tracks all three concerns in one place

### Integration with electron-updater

The existing `electron-updater` integration (`updater.ts:17-71`) should be:
1. Connected to the Release Coordinator (not called independently)
2. Given its own notification sub-channel (`update:exe-status`)
3. Configured to NOT auto-download (let the coordinator control timing)
4. Used only for the EXE download + install path

## 42. Release Synchronization Contract

> **Status:** PROPOSED

### The Governing Invariant

1. Renderer files are downloaded to a NEW cache directory (not the active one)

## 43. Health / Activation Gate

> **Status:** PROPOSED

### Definition of "Release Successfully Activated"

A release is confirmed as activated when ALL of the following pass:

| Check | How Verified | Failure Action |
|---|---|---|
| Main process starts | `app.whenReady()` resolves | App cannot start — user sees error dialog |
| Renderer loads | `ProtocolHandler` serves index.html | Fallback to bundled dist |
| Active Release ID matches expected | `getActiveRendererPath()` returns non-null | Use bundled dist |
| Renderer assets are complete | `isRendererCached()` checks `index.html` exists | Use bundled dist |
| Required DB schema exists | `resolveSchemaCompatibility()` returns 'ok' | Block startup |
| Required RPCs exist | `verifyCriticalFunctions()` checks 7 functions | Block startup |
| Database connectivity works | `bootstrapLocalDatabase()` succeeds | Show error, continue without DB |
| Critical bootstrap succeeds | `OFFLINE_READY` flag or sync running | Continue, retry sync later |

### Minimum Practical Health Gate

For the current implementation, the minimum health gate is:

```
1. app.whenReady()                           ← always passes (or app doesn't start)
2. Renderer serves index.html                ← automatic (fallback to bundled)
3. Schema compatibility = 'ok' or 'needs-migration'  ← hard gate
4. Critical functions verified               ← hard gate
```

This is what `main.ts` currently enforces. It's sufficient for basic operation but doesn't verify:
- That the activated renderer is the INTENDED one (only that SOME renderer is available)
- That all 290 RPCs are present (only checks 7)
- That the renderer's `build-manifest.json` matches the activated build

### Proposed Enhanced Health Gate

```
1. Main process starts
2. Activated renderer's build-manifest.json matches pendingRendererBuildId
3. All expected asset files exist in renderer cache
4. Schema version >= renderer's required_schema_version
5. All critical RPCs present (expanded list)
6. Database connectivity works
7. Initial/incremental sync completes (or is in progress)
```

## 44. Rollback Strategy

> **Status:** PROPOSED

### Renderer Rollback

**Current:** NONE.
**Proposed:** Keep the previous renderer cache directory. On activation failure, revert the `renderer-active-build` marker to the previous build ID.

```
renderer-cache/
├── {build-A}/    ← previous (known-good)
├── {build-B}/    ← current (failed health check)
└── renderer-active-build → build-A (reverted)
```

**Implementation:** Single line in `UpdateState.ts` — maintain `previousBuildId` alongside `appliedBuildId`.

### Database Migration Rollback

**Current:** Transactional rollback on failure. No rollback on success.
**Proposed:** No change. This is the correct behavior. A migration that applies successfully MUST be forward-compatible. If it breaks the renderer, the fix is a new migration, not rolling back.

**Exception:** If a migration applies but the app cannot start (critical function check fails), the user must:
1. Restore from backup (pre-migration backup is already taken)
2. Or install a newer EXE that includes the fix

### EXE Rollback

**Current:** electron-updater supports `allowDowngrade: false` (line 24 of updater.ts).
**Proposed:** No change. Downgrading the EXE is dangerous (newer schema + older code). The user should reinstall manually if needed.

### Health Check Failure Rollback

If the health check fails after activation:
1. Revert `renderer-active-build` to previous build
2. Revert `appliedBuildId` in state file
3. Log the failure
4. Trigger retry on next startup

This requires maintaining a "last known good" pointer that survives across restarts.

   - Renderer hot-swap (via protocol handler + file cache) ✓ already implemented

   - The EXE updater IS disconnected — this IS an architecture gap

   - The Electron packaging model (ASAR + extraResources) is correct for this use case

   - The migration engine is correct
   - The retry/backoff logic is correct
   - Only the **integration layer** needs work, not the foundations

**Option B** — the existing Electron architecture can support the target with:

1. A `ReleaseCoordinator` that wraps the three update paths (renderer, migrations, EXE)

## 48. Final Release Contract Design

> **Status:** DECIDED (principles) / PROPOSED (technical contract)
> **Date:** 2026-08-17

### 48.1 Purpose

This section defines the canonical Release Contract for the Desktop Release Synchronization system. It translates the approved business/operational release principles into a precise technical contract that the implementation must satisfy.

The contract answers one governing question:

> **"How does one published project release become one synchronized Desktop release?"**

---

### 48.2 Release Definition

> **Status:** DECIDED

A **Release** is the complete state of the project at a specific commit. It is NOT a partial snapshot. It includes every component that the project produces:

- Web Renderer (JS, CSS, HTML, static assets)
- Database schema (baseline + migrations)
- Database functions/RPCs (all 290+)
- Database views and triggers
- Main Process code
- Preload script
- IPC contracts
- Native dependencies
- Electron runtime requirements
- Configuration

A Release is **immutable**. Once published, it does not change. A new commit produces a new Release.

A Release may contain any combination of changes:

| Change Type | Example |
|---|---|
| Renderer only | New React component, CSS fix, new page |
| Renderer + Database | New screen backed by new table + migration + RPC |
| Renderer + Main Process | New IPC handler for new renderer feature |
| Renderer + Preload/IPC | New IPC channel for new renderer capability |
| Renderer + Database + EXE | Full-stack feature requiring new native dependency |
| Full-stack Release | Electron version upgrade + all of the above |
| Database only | Migration fixing a bug in an RPC function body |
| Main Process only | Fix in startup logic, migration engine fix |
| EXE only | Electron security patch |

---

### 48.3 Authoritative Release Rule

> **Status:** DECIDED

The **latest officially published project Release** is the authoritative target for Desktop.

```
Release A published → Desktop target = Release A
Release B published → Desktop target = Release B
```

A Release becomes **authoritative** (eligible for Desktop synchronization) when ALL of the following are true:

| Condition | Current Mechanism | Required for Authoritativeness |
|---|---|---|
| Source code is committed to `main` | Git push | YES |
| Web build succeeds | GitHub Actions `build` job | YES |
| Web deployment succeeds | GitHub Actions `deploy` job | YES |
| `build-manifest.json` is served | GitHub Pages CDN | YES |
| All renderer assets are served | GitHub Pages CDN | YES |
| Database migrations are committed | Git push (in same commit) | YES |
| EXE artifact is published (if needed) | GitHub Releases (manual or CI) | YES |

**The Desktop must NOT synchronize to a partially published Release.** If the Web is deployed but the database migrations for that Release are not yet committed, the Desktop must not attempt to apply a migration that doesn't exist yet.

**Current gap:** The `build-manifest.json` on GitHub Pages is the sole trigger. There is no mechanism to verify that database migrations for that Release are actually available via the GitHub API. The `required_schema_version` field provides a version number but not the migration files themselves.

**Proposed solution (PROPOSED):** The Release manifest should include a `release_readiness` flag or the manifest should only be published after all artifacts are verified available. This is a CI/CD concern that does not require code changes to the Desktop — it requires the deployment pipeline to guarantee manifest availability only when all Release artifacts are published.

### 48.4 Release Identity

> **Status:** PROPOSED

The **Release Identity** uniquely identifies one complete project Release across all components.

#### Why `commit_hash` Is the Release Identity

| Candidate | Uniqueness | Scope | Verifiability | Verdict |
|---|---|---|---|---|
| `commit_hash` | Collision-resistant (SHA-1, 40 hex chars) | Identifies exact code state of ALL components | Verifiable against git repository | **SELECTED** |
| `build_id` (short SHA) | 7 chars, collision possible at scale | Renderer build only | Verifiable against git | INSUFFICIENT — renderer only |
| `app_version` (semver) | Non-unique across commits (same version can be rebuilt) | EXE only | Verifiable against package.json | INSUFFICIENT — EXE only |
| `schema_version` (integer) | Non-unique (same version can have different migration sets) | Database only | Verifiable against manifest.json | INSUFFICIENT — DB only |
| Composite key | Unique but complex | All components | Requires coordination | OVER-ENGINEERED |

**Decision:** `commit_hash` is the Release Identity because:
1. It is generated by Git and is immutable once committed
2. It identifies the exact state of every file in the repository at that commit
3. It is already generated by CI and available in the deployment pipeline
4. It can be verified by the Desktop against the GitHub API
5. It naturally encompasses renderer, database, main process, preload, and configuration

#### Release Identity Structure (PROPOSED)


### 48.8 UPDATED Definition

> **Status:** DECIDED

Desktop is **UPDATED** if and only if EVERY artifact required by the Target Release satisfies ALL of the following conditions:

```
UPDATED ⟺
  ∀ artifact ∈ TargetRelease.artifacts:
    artifact.exists ∧
    artifact.integrity_verified ∧
    artifact.compatibility_satisfied ∧
    artifact.applied_or_installed ∧
    artifact.active WHERE applicable ∧
    artifact.health_confirmed ∧
    artifact.release_identity = TargetRelease.release_id
```

In plain language:

1. **Exists** — The artifact file/data is present on disk or in the database
2. **Integrity verified** — Hash/signature matches the Release manifest
3. **Compatibility satisfied** — The Desktop meets the artifact's minimum requirements
4. **Applied/installed** — The artifact is in its final location (not staging)
5. **Active where applicable** — The renderer is the active directory; the EXE is the running binary
6. **Health confirmed** — Post-activation health check passes
7. **Release identity matches** — The artifact corresponds to the Target Release, not an older one

**If ANY artifact fails ANY condition: Desktop is NOT UPDATED.**

#### Per-Artifact UPDATED Conditions

| Artifact | EXISTS | INTEGRITY | COMPATIBILITY | APPLIED | ACTIVE | HEALTHY | IDENTITY |
|---|---|---|---|---|---|---|---|
| Renderer | File exists in cache | All assets pass SHA-256 | Schema version ≥ required | Downloaded to cache dir | `renderer-active-build` points to it | `isRendererCached()` passes | build_id matches manifest |
| Database Schema | schema_migrations table exists | N/A (transactional) | App version ≥ min_app_version | All pending migrations applied | N/A (always active) | Critical functions verified | schema_version ≥ manifest required |
| Database RPCs | Functions exist in pg_proc | N/A | N/A | Created by migration | N/A (always active) | Verified by startup check | Part of schema_version |
| Desktop EXE | Running binary matches expected version | N/A (ASAR integrity) | Electron version ≥ min | Installed | Running binary | App starts successfully | app_version = manifest app_version |

### 48.10 EXE Update Relationship

> **Status:** PROPOSED

The custom Renderer/Database updater and the `electron-updater` (EXE updater) must be parts of **ONE Release Synchronization system**, not two unrelated systems.

#### Current State

```
Custom UpdateCoordinator          electron-updater
(Renderer + Migrations)           (EXE replacement)
        │                                │
   GitHub Pages                    GitHub Releases
   GitHub Contents API              NSIS installer
        │                                │
   Shared IPC channel: update:status     │
        │                                │
        └──────── CONFLICT ──────────────┘
```

**Problem:** The two systems share the `update:status` IPC channel and can overwrite each other's status messages. Neither knows about the other's actions. An EXE update could destroy a carefully staged renderer update.

#### Proposed Unified Architecture (PROPOSED)

```
                    PUBLISHED RELEASE
                           │
                    RELEASE COORDINATOR
                    (single entry point)
                           │
              ┌────────────┼────────────┐
              │            │            │
         Renderer      Database      EXE
         Updater       Updater       Updater
              │            │            │
         GitHub Pages  GitHub API   GitHub Releases
              │            │            │
              └────────────┼────────────┘
                           │
                    SINGLE NOTIFICATION
                    (no IPC conflicts)
```

#### Release Coordinator Responsibilities

1. **Single manifest fetch** — one HTTP request determines what changed
2. **Ordered execution:**
   - Phase 1: Check manifest → determine required updates
   - Phase 2: Apply DB migrations (if needed) — must complete before renderer
   - Phase 3: Download renderer (if needed) — must complete before activation
   - Phase 4: Download EXE (if needed) — staged, not installed yet
   - Phase 5: Health check
   - Phase 6: Notify user (restart required)
3. **Single state file** — all artifact state in one place
4. **Single notification channel** — no IPC conflicts
5. **EXE safety** — EXE is downloaded but NOT installed during the current session; it installs on quit

#### EXE Installation Safety

> **Status:** DECIDED

> EXE replacement must not destroy the currently installed working state before the new EXE is safely staged.

The EXE update path must:

1. Download the new NSIS installer to a staging directory
2. Verify the download (signature, file size, hash)
3. Stage the installer (mark it for installation on quit)
4. **NOT install while the app is running**
5. On user-initiated restart or quit: launch the NSIS installer, which replaces the running EXE
6. The NSIS installer handles atomic file replacement (standard NSIS behavior)

This ensures the current working EXE is never destroyed before the new one is verified and staged.

### 48.11 Activation Contract

> **Status:** PROPOSED

Activation is the step where a downloaded/staged artifact becomes the active, running artifact.

#### Renderer Activation

```
ACTIVATION SEQUENCE:
  1. Read pending_renderer_build_id from state
  2. Verify isRendererCached(buildId) — ALL files present
  3. Write buildId to renderer-active-build marker file
  4. Update state: applied_build_id = buildId, pending = null
  5. State is now: renderer is ACTIVE

NEXT STARTUP:
  1. Read renderer-active-build marker
  2. Verify isRendererCached(buildId)
  3. Call setActiveRendererDirectory(path)
  4. ProtocolHandler serves from new directory
```

**Safety invariant:** The existing renderer remains active until the new renderer is fully downloaded, verified, and the marker file is atomically swapped. If activation fails, the marker is not updated and the old renderer remains active.

#### Database Migration Activation

Migrations are activated at the moment they are COMMITTED in the database transaction. There is no separate "activation" step. The `schema_migrations` row is written atomically with the DDL.

**Safety invariant:** If a migration fails, ROLLBACK undoes all DDL. The `schema_migrations` row records `status='failed'`. The database is in the same state as before the migration attempt.

#### EXE Activation

EXE activation happens when the user restarts the application and the NSIS installer replaces the running binary.

**Safety invariant:** The current EXE continues running until the user explicitly restarts. The new EXE is staged but not active until the restart event.

### 48.13 Failure Safety Invariants

> **Status:** DECIDED

These invariants must hold at all times, across all failure modes.

#### Invariant 1: Known-Good Release Remains Recoverable

> **Never sacrifice the currently working Desktop Release in order to install a new Release.**

- The current renderer cache directory is never deleted until a NEW renderer is fully downloaded and verified
- The current EXE is never replaced until a NEW EXE is staged and the user restarts
- The current database schema is never left in a partially migrated state

#### Invariant 2: Incomplete Downloads Cannot Become Active

- A renderer is only activated after ALL files in the manifest are downloaded AND SHA-256 verified
- A partial download (crash mid-download) does NOT set `pending_renderer_build_id`
- The `renderer-active-build` marker is only written after `isRendererCached()` returns true for ALL expected files

#### Invariant 3: Failed Verification Cannot Become Active

- If any asset fails SHA-256 verification, the download is rejected
- If the manifest cannot be fetched, no updates are attempted
- If the manifest is malformed, it is rejected

#### Invariant 4: Failed Migrations Cannot Be Treated as Applied

- If a migration fails, the transaction is ROLLBACK'd
- The `schema_migrations` row is recorded as `status='failed'`, not `status='applied'`
- The application refuses to start if a migration fails

#### Invariant 5: New Renderer Cannot Activate Against Incompatible Schema

- Migrations are applied BEFORE renderer activation
- If migrations fail, `pending_renderer_build_id` is not set
- The renderer is only activated at the next startup, after migrations have already succeeded

#### Invariant 6: EXE Replacement Does Not Destroy Working State

- The new EXE is downloaded to a staging directory
- The current EXE continues running
- The NSIS installer replaces the EXE only on user-initiated restart
- If the download fails, the current EXE is untouched

#### Invariant 7: Failed Health Checks Do Not Leave Desktop Permanently Broken

- If the health check fails after activation, the system falls back to the previous renderer
- If the database is incompatible, the app refuses to start (safe failure)
- The retry mechanism ensures transient failures are recoverable

#### Invariant 8: Network Failure Is Not Treated as Release Corruption

- If the manifest cannot be fetched, the system reports "offline" and retries
- If individual assets fail to download, the system retries
- Network failures never modify the state file's `applied_build_id` or `applied_version`

#### Invariant 9: Retry Is Safe and Idempotent

- Retrying a completed download is a no-op (file already exists with correct hash)
- Retrying a completed migration is a no-op (version already applied)
- Retrying an activation is a no-op (marker already points to correct build)
- The exponential backoff prevents hammering the server

#### Invariant 10: Release State Survives Restart/Crash/Power Loss

- All state is persisted to `update-state.json` before any destructive operation
- On restart, the system reads the state file and resumes from the last known state
- Corrupted state files are handled gracefully (return to default state)

### 48.14 Retry and Recovery Contract

> **Status:** PROPOSED

#### Retry Policy

| Condition | Retry? | Backoff | Max Retries |
|---|---|---|---|
| Manifest fetch failure | YES | Exponential: 5s, 10s, 20s, ... 30m cap | Unlimited |
| Renderer download failure | YES | Exponential (same) | Unlimited |
| Migration download failure | YES | Exponential (same) | Unlimited |
| Migration apply failure | NO (blocks startup) | N/A | N/A (user must fix) |
| EXE download failure | YES | Exponential (same) | Unlimited |
| Health check failure | YES | On next startup | Unlimited |
| Network offline | YES | On network restoration or periodic retry | Unlimited |

#### Recovery Strategies

| Failure | Recovery |
|---|---|
| Renderer download partial | Retry from scratch (no resume); old renderer remains active |
| Renderer activation fails | Fall back to previous renderer (if available) or bundled dist |
| Migration apply fails | App refuses to start; user must restore from backup or install newer EXE |
| EXE download fails | Current EXE continues; retry on next cycle |
| EXE install fails | NSIS handles rollback; current EXE remains |
| State file corrupted | Return to default state; re-check on next cycle |
| Health check fails | Fall back to previous renderer; retry on next startup |

### 49.3 Release Identity Decision

**Status: DECIDED**

**Decision:** `commit_hash` (full 40-character Git SHA) is the canonical Release identity.

**Repository evidence:**
- `deploy.yml:40`: `COMMIT_HASH=$(git rev-parse HEAD)` — full 40-char SHA
- `vite.config.ts:58`: `__COMMIT_HASH__: JSON.stringify(process.env.COMMIT_HASH || 'dev')`
- `build-manifest.json`: contains `"commit_hash"` field with full SHA
- `desktop-release.yml:46`: `${{ github.sha }}` — same full SHA from GitHub context

**Why commit_hash is sufficient:**
1. **Renderer**: Generated from the commit. `build_id` (abbreviated SHA) is a subset of `commit_hash`. The renderer is uniquely identified by `commit_hash`.
2. **Database migrations**: Committed in the same repository. `commit_hash` determines which migrations are available. `required_schema_version` in the manifest tells the app which migrations the renderer expects.
3. **Main Process / Preload / Electron**: Part of the EXE artifact. The EXE is built from the same commit. `app_version` in `desktop/package.json` identifies the EXE version, but this is a separate artifact concern.
4. **Configuration**: Bundled in `extraResources` during EXE build. Determined by `commit_hash`.

**Why alternatives were rejected:**
- `build_id` (abbreviated SHA): 7-12 characters, not guaranteed unique across branches. Insufficient as Release identity.
- `app_version` (1.4.0): Manually bumped, 1:many relationship with commits. Multiple commits can share one version. Cannot identify which commit the renderer or migrations came from.
- Composite `commit_hash + app_version`: Adds complexity without benefit. The EXE version is an artifact of the Release, not part of the Release identity.

**Caveat:** `app_version` is required for EXE artifact identification (electron-updater uses it from `latest.yml`). It is an attribute of the EXE artifact, not part of the Release identity. The Release Coordinator must track `app_version` as an EXE artifact version, not as the Release identity.

### 49.4 Release Artifact Decision

**Status: DECIDED**

**Decision:** A Release is a single atomic identity (`commit_hash`). Its artifacts are CONDITIONAL — only artifacts that changed are required by Desktop. The Release Identity and Release Artifact requirement are distinct concepts.

**Release Identity vs Release Artifacts:**

A Release is identified by `commit_hash`. This identity represents the complete project state at a point in time. However, not every artifact type changes with every Release. The system detects which artifacts changed and only synchronizes those.

**Repository evidence:**
- `ReleaseManifest.ts:44-46` → `compareManifests()` independently computes three flags:
  - `rendererChanged = remote.build_id !== localBuildId`
  - `schemaNeedsUpgrade = remote.required_schema_version > localSchemaVersion`
  - `appNeedsUpgrade = compareVersions(remote.app_version, localAppVersion) > 0`
- `UpdateCoordinator.ts:144-153` → skips renderer download when `rendererChanged=false`, skips migrations when `schemaNeedsUpgrade=false`
- `UpdateCoordinator.ts:117` → EXE short-circuit returns immediately when `appNeedsUpgrade=true`

**Artifact model — conditional requirement:**

| Artifact | Detected By | When Changed | When Not Changed |
|---|---|---|---|
| **Renderer** | `remote.build_id !== localBuildId` | Download and activate renderer assets | Skip entirely — zero network requests, zero file I/O |
| **Database** | `remote.required_schema_version > localSchemaVersion` | Download and apply migration SQL | Skip entirely — zero GitHub API calls, zero DB connections |
| **EXE** | `compareVersions(remote.app_version, localAppVersion) > 0` | Stage EXE via electron-updater, require restart | Skip entirely — no electron-updater interaction |

**Sub-artifacts within EXE:**
- Main Process code (compiled TypeScript)
- Preload script (compiled TypeScript)
- Electron runtime (Chromium + Node.js)
- Native dependencies (pg, better-sqlite3)
- Configuration (extraResources: schema.sql, migrations, pg-binaries, provision, supabase.json)

These are NOT independently versioned. They are all produced by a single `electron-builder` invocation from a single commit. When `appNeedsUpgrade=false`, none of these are touched.

**Why the previous "all three required" statement was wrong:**
The previous report stated "Three independent groups, all required" but also said "EXE publish is NOT a prerequisite for renderer/DB sync." These are contradictory. The correct model is: a Release CONTAINS all three artifact types conceptually, but Desktop only synchronizes artifacts that CHANGED. A Release can contain only renderer changes (no DB, no EXE), only DB changes, only EXE changes, or any combination.

**Practical examples:**

| Release | rendererChanged | schemaNeedsUpgrade | appNeedsUpgrade | Desktop Does |
|---|---|---|---|---|
| CSS fix only | true | false | false | Downloads renderer assets only |
| New migration only | false | true | false | Applies migrations only |
| Main process bug fix | false | false | true | Stages EXE, requires restart |
| Full release | true | true | true | Downloads renderer, applies migrations, stages EXE, restarts |
| Config-only change | false | false | false | Nothing — system is current |

### 49.5 Release Readiness Decision

**Status: DECIDED**

**Decision:** A Release becomes eligible for Desktop synchronization when ALL of the following are true:

| Condition | Evidence | Failure Mode |
|---|---|---|
| Web build succeeds | `deploy.yml` → `npm run build` | No `dist/` produced |
| Deployment to GitHub Pages succeeds | `deploy.yml` → GitHub Pages action | `build-manifest.json` not served |
| `build-manifest.json` is accessible | `RendererUpdater.ts` → fetches from `BASE_URL` | Desktop can't detect new Release |
| Renderer assets are accessible | `RendererUpdater.ts` → downloads from `ASSETS_URL` | Partial download, corrupted cache |
| Database migrations are committed | `migrations/manifest.json` → lists SQL files | Desktop can't find migration SQL |
| EXE artifact is published (when needed) | `desktop-release.yml` → `latest.yml` on GitHub Releases | electron-updater can't detect new EXE |

**Release Ready state:** NOT implemented as a formal state machine state. The system infers readiness by attempting to fetch `build-manifest.json` and checking HTTP 200 + valid JSON. If the manifest is not served or is malformed, the update check fails gracefully.

**EXE publish is NOT a prerequisite for renderer/DB updates.** The `desktop-release.yml` workflow is triggered by a separate tag push or manual workflow dispatch. A Release can be fully synchronized (renderer + DB) without an EXE update. EXE updates are a separate concern that the Release Coordinator orchestrates independently.

### 49.6 Release Manifest Decision

**Status: DECIDED**

**Decision:** Extend the existing `build-manifest.json` format. Do NOT create a separate manifest file.

**Current format** (from `vite.config.ts:95-135`):
```json
{
  "build_id": "b999731",
  "commit_hash": "full-40-char-sha",
  "app_version": "1.0.0",
  "required_schema_version": 7,
  "assets": {
    "assets/main.js": "sha256-hash",
    "assets/main.css": "sha256-hash",
    "index.html": "sha256-hash",
    ...
  }
}
```

**Required extensions:**
- `release_date` — ISO 8601 timestamp of when the Release was published (currently not present)
- All existing fields are already present and correct

**Why extend rather than replace:**
- `build-manifest.json` is already fetched by `RendererUpdater.ts` at `BASE_URL`
- Adding fields is backward-compatible (existing clients ignore unknown fields)
- A separate `release-manifest.json` would require a second HTTP fetch and a second file to keep in sync

**Conceptual JSON schema (extended):**
```json
{
  "build_id": "string — abbreviated commit SHA, renderer version identifier",
  "commit_hash": "string — full 40-char Git SHA, Release identity",
  "app_version": "string — semantic version from desktop/package.json, EXE artifact version",
  "release_date": "string — ISO 8601 timestamp",
  "required_schema_version": "number — minimum DB schema version the renderer requires",
  "assets": {
    "<path>": "string — SHA-256 hex digest of file content"
  }
}
```

**What the manifest does NOT contain:**
- Main Process code hash — part of EXE artifact, identified by `app_version`
- Preload code hash — part of EXE artifact
- Electron runtime version — bundled with EXE
- Configuration hash — bundled in extraResources with EXE
- EXE artifact hash — identified by `app_version` + electron-updater's `latest.yml`

### 49.7 Synchronization State Decision

**Status: DECIDED**

**Decision:** Two distinct state models must be maintained: Remote Release Contract and Local Synchronization State.

#### Remote Release Contract
This is the `build-manifest.json` fetched from GitHub Pages. It is **not persisted** — it is fetched fresh on each update check. If the fetch fails, the last-known-good state is used.

#### Local Synchronization State
This is persisted in `{userData}/ahram-desktop/update-state.json`. It must survive restart, crash, and power loss.

**Minimum persistent state:**

| Field | Type | Purpose | Survives |
|---|---|---|---|
| `appliedBuildId` | `string \| null` | Renderer build ID currently active | All |
| `appliedAppVersion` | `string \| null` | EXE version currently running | All |

### 49.8 Release Coordinator Decision

**Status: DECIDED**

**Decision:** Expand the existing `UpdateCoordinator` into the canonical Release Coordinator. Do NOT replace it.

**Current responsibilities of UpdateCoordinator:**
1. Fetch remote manifest (`checkForUpdates`)
2. Download renderer assets (`downloadNewRenderer`)
3. Download and apply migrations (`downloadAndApplyMigrations`)
4. Activate pending renderer (`activatePendingRenderer`)
5. Error handling and retry (`performFullUpdateCycle`)

**New responsibilities to add:**
1. EXE update detection (compare `appliedAppVersion` vs remote `app_version`)
2. EXE update orchestration (delegate to electron-updater, track state)
3. Health gate (after activation, verify the application is healthy)
4. Update ordering (ensure migrations complete before renderer activation)
5. IPC coordination (prevent simultaneous custom updater + electron-updater execution)

**Authority:** The Release Coordinator has exclusive authority over:
- When to check for updates
- What order to apply artifacts
- When to activate the new renderer
- When to trigger EXE update
- When to restart
- When to declare the system UPDATED

**Inputs:**
- Remote Release Contract (fetched from GitHub Pages)
- Local Synchronization State (read from update-state.json)
- Electron-updater status (for EXE updates)

**Outputs:**
- Updated renderer cache
- Applied database migrations
- Activated renderer pointer
- Updated EXE (via electron-updater)
- Restart signal
- Status updates to renderer (via `update:status` IPC)

**IPC Conflict Resolution:**
The existing `update:status` channel is shared between the custom updater and electron-updater. The Release Coordinator must serialize access. Two options exist:
1. **Lock-based:** The Release Coordinator acquires a mutex before running any update system. If the lock is held, the other system's request is rejected or queued.
2. **Single-writer:** Only the Release Coordinator writes to `update:status`. Both systems report to the coordinator, which forwards to the renderer.

**Decision:** Option 2 (single-writer). The Release Coordinator is the sole writer to `update:status`. Both the custom updater and electron-updater report status to the coordinator, which normalizes and forwards.

### 49.9 Update Ordering Decision

**Status: DECIDED**

**Decision:** Database Migrations → Renderer Download → Renderer Activation → EXE Update → Restart → Health Check

**Justification with repository evidence:**

**Step 1: Database Migrations (while old renderer is still active)**
- Evidence: `MigrationUpdater.ts:226-260` applies migrations via `BEGIN`/`COMMIT`/`ROLLBACK`. Each migration is a separate transaction.
- Why first: Migrations may add tables/columns that the NEW renderer needs. The OLD renderer does not call new RPCs (it doesn't know about them). Running migrations while the old renderer is active is safe because the old renderer only uses existing schema.
- Forward compatibility: The old renderer continues working because `REQUIRED_SCHEMA_MAP` defines a floor. A schema at version 7 satisfies `>= 3` (app 1.4.0's requirement).

**Step 2: Renderer Download (can happen in parallel with Step 1)**
- Evidence: `RendererUpdater.ts` downloads files from GitHub Pages. This is pure network I/O with no database interaction.
- Why parallel is safe: Renderer download reads no database state. It writes to `renderer-cache/{buildId}/` which is separate from the active renderer.

**Step 3: Renderer Activation (after both Steps 1 and 2 complete)**
- Evidence: `activatePendingRenderer()` writes `renderer-active-build` marker file. `main.ts:259-263` reads it on next startup.
- Why after migrations: The new renderer may call new RPCs that only exist after migration. If the new renderer is activated before migrations complete, RPC calls will fail.
- Why before EXE: The new renderer is compatible with the current EXE (renderer is independent of EXE version). The new renderer is NOT compatible with the old schema (if migrations were not applied).

**Step 4: EXE Update (optional, after renderer activation)**
- Evidence: `electron-updater` manages EXE download and NSIS installation via `quitAndInstall`.
- Why optional: EXE updates are not always required. The Release Coordinator determines if `appliedAppVersion` < remote `app_version`.
- Why after renderer: The new renderer must be working before triggering EXE replacement, which requires a restart.

**Step 5: Restart (after EXE update if triggered, or after renderer activation)**
- Evidence: `updater.ts` → `update:restart` → `app.relaunch()` + `app.quit()` (raw restart for renderer-only updates); `update:install` → `autoUpdater.quitAndInstall(false, true)` (NSIS installer restart for EXE updates).
- Why after all artifacts are applied: Restart is the point of no return. After restart, the new EXE loads the new renderer and new schema.

**Step 6: Health Check (after restart)**
- Evidence: `HealthChecker.ts:56-78` → verifies DB connectivity, schema version, quarantine status. `SchemaMigrator.ts:43-78` → `verifyCriticalFunctions()` checks required RPCs.
- Why last: The health gate confirms that the new Release is actually working. Only after passing the health gate can the system declare UPDATED.

**Compatibility matrix (justifying the order):**

| Scenario | Result |
|---|---|
| Old Renderer + New Schema (migrations applied, renderer not yet) | ✅ SAFE — old renderer only uses schema floor (>= 3), new schema satisfies this |
| New Renderer + Old Schema (renderer activated, migrations not yet) | ❌ UNSAFE — new renderer may call RPCs that don't exist in old schema |
| New Renderer + New Schema + Old EXE | ✅ SAFE — renderer is independent of EXE version |
| New Renderer + New Schema + New EXE | ✅ SAFE — all artifacts from same Release |
| Old Renderer + New Schema + New EXE | ✅ SAFE but incorrect — old renderer on new schema is functional but not the target |

### 49.11 Atomic Activation Decision

**Status: DECIDED**

**Decision:** Activation is NOT atomic in the filesystem sense. Safety is ensured by the state machine, not by atomic operations. Renderer rollback is automatic on health gate failure.

**Renderer activation:**
- Mechanism: `setActiveRendererBuild(buildId)` writes the build ID string (10-40 bytes) into `{stateDir}/renderer-active-build`.
- Atomicity: A single small-file write is effectively atomic on NTFS (the target filesystem). The write is either complete or not. Partial writes of a 40-byte file are not a realistic concern.
- Crash safety: If the app crashes after writing the marker but before the next startup reads it, the marker persists on disk. The next startup reads the marker and activates the correct renderer.

**Previous build ID capture (for rollback):**
- Before `setActiveRendererBuild(buildId)` overwrites the marker, the current marker value is read and saved as `previousAppliedBuildId` in `update-state.json`.
- This captures the last-known-good build ID before activation.
- Evidence: `UpdateState.ts` → `renderer-active-build` marker file contains the current build ID. `getActiveRendererPath()` reads it at startup. The old value is available until overwritten.

**Renderer rollback mechanism:**
- If the health gate fails after activation, the Release Coordinator writes `previousAppliedBuildId` back to `renderer-active-build`, updates `appliedBuildId` in state, and calls `app.relaunch()` + `app.quit()`.
- On restart, `getActiveRendererPath()` reads the restored old build ID. `renderer-cache/{oldBuildId}/` still exists on disk (never deleted). The old renderer is served.
- The rollback is fully automatic — no user intervention required. The user sees a brief restart.

**Crash safety of rollback:**
- If the app crashes between marker write and state save during rollback: marker has old build ID, state still has new. On next restart, marker is read (old build ID), old renderer is served. `activatePendingRenderer()` would try to activate again (since `pendingRendererBuildId` was nulled during the original activation). This is harmless because `setActiveRendererBuild` is idempotent.
- If the app crashes during `app.relaunch()`: The marker already has the old build ID. On next manual launch, old renderer is served.

**Database activation:**
- Mechanism: Each migration runs in a `BEGIN`/`COMMIT`/`ROLLBACK` transaction.
- Atomicity: True atomicity per migration. If migration 5/7 fails, it rolls back. The DB remains at schema version 4.
- Crash safety: If the process crashes during a migration, the PostgreSQL transaction is rolled back by the server. The `schema_migrations` table records the last committed version.
- No rollback needed: Migrations are forward-only. A failed migration leaves the DB in the previous state.

**EXE activation:**
- Mechanism: NSIS installer replaces the EXE files and relaunches the app.
- Atomicity: NSIS has built-in rollback. If the installer fails, the old EXE is restored.
- Crash safety: If the process crashes during NSIS installation, the installer's rollback mechanism restores the previous version.
- No rollback needed: NSIS handles it.

### 49.12 Health Gate Decision

**Status: DECIDED**

**Decision:** Minimum health gate with 6 checks. Evidence-based — no arbitrary expansion.

**The minimum meaningful health gate:**

| Check | Source | What It Verifies | Failure Action |
|---|---|---|---|
| 1. Main process started | `main.ts` → `app.whenReady()` | Electron process initialized | App cannot start — user sees crash dialog |
| 2. Renderer loaded | `ProtocolHandler.ts` → `ahram://` serves `index.html` | Renderer files are accessible and valid | Falls back to bundled `dist/` — degraded but functional |
| 3. Renderer IPC confirm | New: renderer sends confirmation to main after mount | Renderer actually rendered and can communicate via IPC | **Triggers automatic renderer rollback** (§49.13) |
| 4. DB connectivity | `HealthChecker.ts:60-78` → `tryConnect(config)` | PostgreSQL is running and reachable | `startAhramService()` attempts to start the service |
| 5. Schema compatibility | `SchemaMigrator.ts:231-260` → `resolveSchemaCompatibility()` | DB schema version >= required version | Returns `needs-migration` — triggers migration download |
| 6. Critical functions exist | `SchemaMigrator.ts:43-78` → `verifyCriticalFunctions()` | Required RPCs exist in `pg_proc` | Returns `missing_functions` — blocks app startup |

**Renderer IPC confirm (new check 3):**
After the renderer mounts, it sends an IPC call to the main process confirming successful load. This is the only reliable signal that the renderer is functional. If this confirmation does not arrive within a timeout (e.g., 10 seconds after window creation), the health gate fails and automatic rollback triggers.

**Why check 3 is necessary:**
The existing health gate (checks 1, 4, 5, 6) verifies the infrastructure (Electron process, PostgreSQL, schema). But it does not verify that the renderer actually rendered. A broken renderer (e.g., JavaScript error preventing mount) would pass all infrastructure checks while the user sees a blank screen. Check 3 closes this gap.

**Why NOT expand beyond 6 checks:**
- IPC contract verification: The preload script (`preload/index.ts`) is built at EXE build time. If the preload is wrong, the app crashes at startup (check 1 catches this).
- Application shell: Covered by check 2 (renderer loaded) and check 3 (renderer confirmed).
- Expected Release ID: Not checked at health gate time. The Release ID is known from the update state, and if the wrong renderer is active, check 3 would fail (the renderer can't confirm if it's broken).
- Renderer integrity: SHA-256 verification happens at download time (`RendererUpdater.ts`). Post-activation re-hashing is unnecessary.

**Critical function evidence (§49.21 resolution):**
The current 7 functions are evidence-based sufficient:
- **V1 (startup-essential):** `login` (called at Desktop login, `database.ts:333`), `validate_session` (called by IPC handler, `database.ts:395`), `check_capability` (called on-demand by ProtectedRoute, `ProtectedRoute.tsx:56`)
- **V2 (core runtime):** `get_unified_orders` (called for sales rep dashboard, `SalesRepWorkDay.tsx:51`)
- **V3 (schema provisioning defense):** `get_inventory_policies`, `set_global_negative_selling_policy`, `set_global_inventory_deduction_status` (called by `ProductManagerPage.tsx`)

The V3 functions are not called at startup but are a legitimate defensive measure: they verify that the database schema is fully provisioned. If any V3 function is missing, it indicates the migration set is incomplete. Keeping them in the gate is justified.

Additional startup RPCs (`get_my_notifications`, `get_my_unread_count`, `ensure_baseline`, `get_unseen_counts`) are all wrapped in error handling and degrade gracefully. They do NOT need to be in the critical gate.

### 49.13 Rollback Decision

**Status: DECIDED**

**Decision:** Automatic renderer rollback on health gate failure. Forward recovery for database. Previous EXE kept on disk.

#### Renderer Rollback (AUTOMATIC)
- **Mechanism:** On health gate failure (check 3 — renderer IPC confirm fails), the Release Coordinator:
  1. Reads `previousAppliedBuildId` from `update-state.json`
  2. Writes `previousAppliedBuildId` to `renderer-active-build` marker file
  3. Updates `appliedBuildId = previousAppliedBuildId` in state
  4. Calls `app.relaunch()` + `app.quit()`
- **When:** Automatically, after post-activation health gate failure. No user intervention.
- **What the user sees:** Brief restart. The application returns to the previous working version.
- **Repository evidence:**
  - `UpdateState.ts` → `rendererCacheDir(buildId)` creates `renderer-cache/{buildId}/` directories
  - `isRendererCached(buildId)` checks `renderer-cache/{buildId}/index.html` existence
  - Old renderer cache is NEVER deleted — confirmed zero cleanup code in entire `main/` directory
  - `ProtocolHandler.ts` → `activeDistDir` is in-memory; restart re-reads marker from disk
  - `app.relaunch()` + `app.quit()` already available in `updater.ts:177-181`
- **Rollback guard:** After rollback, the failed build ID is recorded in state to prevent re-applying it on the next update cycle.

#### Database Rollback (NOT APPLICABLE — Forward Recovery)
- **Mechanism:** NONE. DDL changes (CREATE TABLE, ADD COLUMN, ALTER TYPE) are not safely reversible.
- **Strategy:** Forward recovery. If migration 5/7 fails, the DB remains at schema 4. The next startup detects `needs-migration` and retries from migration 5. If migration 5 is genuinely broken, the user must manually fix the SQL or restore from backup.
- **Repository evidence:** `MigrationUpdater.ts:226-260` → `BEGIN`/`COMMIT`/`ROLLBACK` per migration. Failed migrations roll back to the previous version. The `schema_migrations` table tracks committed versions.
- **No automatic downgrade:** Downgrade SQL would need to be written for each migration, doubling the maintenance burden and introducing regression risk. Not justified for the current deployment model.

#### EXE Rollback (NSIS Built-in)
- **Mechanism:** NSIS installer has built-in rollback. If installation fails, the old EXE is restored.
- **When:** If the new EXE crashes on startup, the user can re-run the previous installer from `release3/`.
- **Repository evidence:** `electron-builder.yml` → NSIS builder with default rollback behavior. `release3/Ahram ERP Setup 1.4.0.exe` exists on disk.
- **Automatic?** NSIS rollback is automatic on installation failure. Post-installation crash recovery is manual (user must reinstall previous version).

### 49.14 Retry Decision

**Status: DECIDED**

**Decision:** Exponential backoff 5s-30min with the existing implementation's formula.

**Retryable errors (network-related):**
| Error | Evidence | Retry Behavior |
|---|---|---|
| DNS failure | `RendererUpdater.ts` → `fetch()` throws | Retry with backoff |
| Network disconnect | `RendererUpdater.ts` → `fetch()` throws | Retry with backoff |
| HTTP 429 (rate limit) | GitHub Pages rate limiting | Retry with backoff (longer backoff may be needed) |
| HTTP 500/502/503 (server error) | GitHub Pages/Actions outage | Retry with backoff |
| Timeout | `fetch()` does not resolve | Retry with backoff |
| Partial download | SHA-256 verification fails | Retry from scratch (no partial resume) |
| Deployment propagation delay | `build-manifest.json` not yet served after deploy | Retry with backoff |

**Non-retryable errors:**
| Error | Evidence | Behavior |
|---|---|---|
| Invalid manifest format | `build-manifest.json` is not valid JSON | Record error, do not retry until next cycle |
| Incompatible Release | `required_schema_version > manifest.schemaVersion` | Record error, do not retry (EXE update required) |
| Application restart failure | `app.relaunch()` fails | Record error, user must manually restart |
| Database connection permanently lost | `HealthChecker.ts` → `tryConnect` fails after service start | Record error, user must check PostgreSQL |

**Backoff formula (from `UpdateState.ts:81-122`):**
```
delay = 5000ms * 2^(retryCount - 1)
maxDelay = 30 * 60 * 1000ms (30 minutes)
nextRetryAt = now + min(delay, maxDelay)
```

**Retry reset conditions:**
- Successful check: `retryCount = 0`, `nextRetryAt = null`, `lastError = null`
- Successful download: `retryCount = 0`, `nextRetryAt = null`, `lastError = null`
- Successful activation: `retryCount = 0`, `nextRetryAt = null`, `lastError = null`

**Maximum practical retry policy:**
- No maximum retry count. The system retries indefinitely with exponential backoff capped at 30 minutes.
- Rationale: Network outages are temporary. There is no reason to stop retrying. The backoff cap prevents hammering the server.
- The `lastSuccessfulCheckAt` field tracks when the last successful check occurred. If this is older than a configurable threshold (e.g., 7 days), the system could surface a "check your connection" message. But this is a UX concern, not a retry concern.

**How it works:**
1. Fresh install: PostgreSQL is initialized, `schema.sql` is executed to create all tables (baseline = version 1), then migrations 0002-0007 are applied.

**Version relationship:** `schema.sql` produces schema version 1 (the baseline). Migrations 0002-0007 produce versions 2-7. ### 49.19 Crash / Power Loss Decision

**Status: DECIDED**

**Decision:** Persistent state at each phase. Reconstruction from remote vs local. Never assume after restart.

| Phase | What Is Persisted | What Can Be Reconstructed | What Must Never Be Assumed After Restart |
|---|---|---|---|
| **CHECK** | `lastCheckedBuildId`, `lastCheckedAt` | Remote manifest can be re-fetched | That the check completed successfully |
| **VERIFY** | `lastCheckedBuildId` (already set) | Manifest hash verification can be re-run | That verification passed |
| **DOWNLOAD** | `pendingRendererBuildId` (on success) | Partial downloads can be retried from scratch | That download was complete |
| **MIGRATE** | Schema version in `schema_migrations` table (committed by SQL transaction) | Failed migrations can be retried (DB is at previous version) | That a partially-started migration committed |
| **STAGE** | `pendingRendererBuildId` (already set) | Renderer cache files on disk can be verified | That staged files are correct |
| **ACTIVATE** | `renderer-active-build` marker file, `appliedBuildId`, `appliedAt` | Marker file can be read from disk | That the activated renderer is working |
| **RESTART** | App process exits; all state is on disk | App relaunches and reads all persistent state | That the restart succeeded (user may need to manually restart) |
| **HEALTH CHECK** | Health status is ephemeral (not persisted) | Health checks can be re-run at any time | That the application is healthy |
| **CONFIRM** | `lastSuccessfulCheckAt`, `retryCount=0`, `nextRetryAt=null`, `lastError=null` | Confirmation can be re-checked by comparing `appliedBuildId` vs remote | Nothing — confirmation is the final state |

**Key invariant:** After any crash or power loss, the system can always determine its state by:
1. Reading `update-state.json` (what was attempted)
2. Reading `renderer-active-build` (what is currently active)
3. Checking `schema_migrations` table (what schema version is committed)
4. Fetching remote `build-manifest.json` (what is the target)

The system never assumes that a phase completed unless there is persistent evidence.

#### D24: Database Migration Forward-Recovery — DECIDED

**Status: DECIDED — Verification Complete (2026-08-18)**

**Decision:** The existing migration engine already satisfies all D24 requirements. No code changes required. The safety properties are verified by code-structure analysis.

**Transaction model (no changes):**

Both `SchemaMigrator.ts` (bundled) and `MigrationUpdater.ts` (remote) use the same pattern:
```
BEGIN
  INSERT INTO schema_migrations (version, name, description, status) VALUES (..., 'applied')
  <DDL SQL>
COMMIT
On failure:
  ROLLBACK
  INSERT INTO schema_migrations (..., 'failed', error_message) ON CONFLICT ...
```

**Why INSERT before DDL is correct:**
- If DDL fails → ROLLBACK undoes both the INSERT and DDL → migration not recorded
- If process crashes after COMMIT → both INSERT and DDL are committed atomically
- If process crashes between BEGIN and COMMIT → PostgreSQL rolls back both

**Recovery behavior:**
- PostgreSQL rolls back uncommitted transactions on client disconnect (documented guarantee)
- Failed migrations recorded with `status = 'failed'` and `error_message`
- On restart, `getSchemaState()` reads `schema_migrations` → failed migrations don't increment `currentVersion` → retried on next startup
- Committed migrations are never reversed (forward-only — no DELETE/DROP in code)

**Proof — Test A: BEGIN/COMMIT/ROLLBACK per migration:**
- Both SchemaMigrator and MigrationUpdater contain BEGIN, COMMIT, ROLLBACK
- PASS

**Proof — Test B: Migration record inserted BEFORE DDL:**
- INSERT INTO schema_migrations comes after BEGIN and before DDL execution
- Atomic rollback guaranteed: if DDL fails, ROLLBACK undoes both
- PASS

**Proof — Test C: Failed migrations recorded with error_message:**
- `status = 'failed'` and `error_message` fields present
- `ON CONFLICT` clause for idempotent recording
- PASS

**Proof — Test D: Each migration is its own transaction:**
- for-loop structure: BEGIN → INSERT → DDL → COMMIT per iteration
- No batched transactions across migrations
- PASS

**Proof — Test E: Committed migrations never reversed:**
- No `DELETE FROM schema_migrations` in either file
- No `DROP TABLE schema_migrations` in either file
- Forward-only confirmed
- PASS

**Limitations:**
- PostgreSQL was not running locally during verification
- Tests verify CODE STRUCTURE (transaction pattern), not live database behavior
- PostgreSQL's transaction guarantees (rollback on disconnect, atomic COMMIT) are well-established PostgreSQL features, not application bugs
- If PostgreSQL itself fails to honor its transaction guarantees, that is a PostgreSQL issue, not an application defect

**Files changed:** None — verification only.

#### D25: Renderer IPC Confirm — DECIDED

**Status: DECIDED — Implementation Proof Complete (2026-08-18)**

**Decision:** The renderer confirms successful initialization/mount to the Electron Main Process through IPC so that a renderer which launches but is functionally broken can fail the health gate.

**Implementation:**

| Aspect | Detail |
|---|---|
| IPC channel/event name | `renderer:confirm-ready` |
| Renderer confirmation point | `App.tsx` — `useEffect` fires after `splashDone === true`; calls `window.api.update.confirmReady()` which sends `ipcRenderer.send('renderer:confirm-ready')` |
| Main-process listener/handler | `main.ts` — `ipcMain.once('renderer:confirm-ready', ...)` registered BEFORE `createMainWindow()`; a second `ipcMain.once` registered inside a `Promise` with `setTimeout` for timeout |
| Timeout | 15,000 ms (15 seconds) |
| Health-gate integration | After window creation, `main.ts` awaits a Promise that resolves on confirmation or after 15s timeout. If `rendererConfirmed === false` after the await, automatic rollback triggers (D20 path) |
| Race protection | Module-level `rendererConfirmed` boolean; single `ipcMain.once` listener registered before window creation prevents race between fast confirmation and await setup |

**Failure behavior:**

```
Renderer fails to confirm
    ↓
15s timeout expires
    ↓
rendererConfirmed remains false
    ↓
rollbackToPreviousRenderer() called
    ↓
If previousAppliedBuildId exists and is cached:
    writes previousAppliedBuildId to renderer-active-build
    updates appliedBuildId = previousAppliedBuildId
    app.relaunch() + app.quit()
    ↓
If no previous renderer:
    logs warning, continues (graceful degradation)
```

**Proof — PASS path:**
- Typecheck `npm run tsc` in `desktop/` — passes with zero errors.
- Renderer confirmation flow: `App.tsx` splash completes → `splashDone = true` → `useEffect` fires → `window.api.update.confirmReady()` → `ipcRenderer.send('renderer:confirm-ready')` → main process `ipcMain.once` fires → `rendererConfirmed = true`.
- Health gate resolves immediately with "PASS (confirmed before wait)" if confirmation arrives before the await.

**Proof — FAIL/timeout path:**
- If renderer crashes before mount or `splashDone` never becomes true, no IPC is sent.
- 15s timeout fires, `rendererConfirmed` remains false.
- `rollbackToPreviousRenderer()` reads `previousAppliedBuildId` from `update-state.json`, writes marker, and triggers restart.
- If `previousAppliedBuildId` is null (first activation or no prior build), rollback is skipped gracefully.

- D22 (dual system mutex) was NOT implemented.
- D23 (activation timing) was NOT implemented.
- D24 (migration forward-recovery) was NOT implemented.

```
    → RETRYING (error occurred, waiting for backoff)
```

## 51. Root Cause Fix — Update Activation & Restart Lifecycle

### 51.1 Renderer Activation Root Cause

**Defect:** `activatePendingRenderer()` was removed from the startup flow during the Phase 5 restructure of `main.ts`.

**Impact:** The pending renderer was never activated on startup. `appliedBuildId` stayed `null` permanently. Every `checkForUpdates()` call compared `null` against the remote manifest's `build_id` → `rendererChanged = true` → renderer already cached → `rendererOk = true` → returned `restart-required` with "Updates applied. Restart to activate." — a perpetual false-positive loop.

**Evidence:**
- `update-state.json`: `appliedBuildId: null`, `pendingRendererBuildId: "f9cc913"`
- `renderer-active-build` marker: FILE NOT FOUND
- Remote manifest: `build_id: "f9cc913"`
- `checkForUpdates()` line 86: `localBuildId = state.appliedBuildId` = `null`
- `compareManifests(remote, null, ...)` → `rendererChanged = true` (always)

**Fix 1 (main.ts:121-127):**
```typescript
// --- Activate pending renderer from previous download (fast, before window) ---
const activated = await activatePendingRenderer()
if (activated) {
  console.log('[Main] Pending renderer activated — restart will apply new UI')
}

// --- Serve from active renderer if marker exists ---
const activeRenderer = getActiveRendererPath()
if (activeRenderer) {
  setActiveRendererDirectory(activeRenderer)
  console.log('[Main] Serving from updated renderer:', activeRenderer)
}
```

**Lifecycle after fix:**
1. `activatePendingRenderer()` → sees `pendingRendererBuildId: "f9cc913"` → renderer cached → writes marker → sets `appliedBuildId: "f9cc913"` → returns `true`
2. `getActiveRendererPath()` → reads marker → returns path
3. `setActiveRendererDirectory(path)` → serves updated renderer
4. `checkForUpdates()` → `appliedBuildId: "f9cc913"` vs remote `"f9cc913"` → `rendererChanged: false` → `isCurrent: true` → "Application is up to date."

### 51.4 public.identities Sync Conflict — Deep Diagnosis

**Exact error:** SQLSTATE 23503 (foreign_key_violation)
- **Constraint:** `fk_public_customer_ownership_history_ibtob9`
- **Failing operation:** `DELETE FROM public.customers WHERE identity_id = '5f295984-fd3d-4c4a-b23e-dca529fb1ee8'`
- **Cascade:** `customer_ownership_history` (2 rows) → `customers` (1 row) → `identities` (1 row)
- **Root cause:** `deleteDuplicateRowAndChildren()` handles only 1 level of FK dependencies. It deletes from tables that directly reference `identities`, but does not recurse into `customer_ownership_history` → `customers`. The `customers` DELETE fails because `customer_ownership_history` still references it.

**Conflict record:**
- Local: `id: 5f295984-fd3d-4c4a-b23e-dca529fb1ee8`, phone: `01065329983`
- Remote: `id: 21d38960-f5d3-404e-859e-8b5c14196290`, phone: `01065329983`
- Same phone, different UUIDs — a duplicate identity created on different instances.

**Synchronization boundary finding:**
`public.identities` IS a custom application table (NOT Supabase Auth-managed). It is the FIRST entry in `SYNC_TABLES` (InitialSync.ts:39) and `sync_get_table_allowlist()` (schema.sql:24395). It stores `phone`, `password_hash`, `identity_type`, `is_active` — all business data. Desktop SHOULD sync and write this table. The issue is NOT the table's inclusion in the sync scope — it is the reconciliation depth.

**Status:** ROOT CAUSE PROVEN AND FIXED. Recursive FK deletion implemented in `deleteDuplicateRowAndChildren()` → `deleteRecursive()`. Post-order DFS traversal discovers and deletes dependencies at arbitrary depth. Cycle detection via visited-set (current recursion path). Production conflict resolved (0 pending remaining). 8/8 recursive tests PASS. 7/7 existing tests PASS. 15/15 total PASS.

## 52. Recursive FK Dependency Resolution — Sync Reconciliation Fix

### 52.1 Implementation

Replaced the single-level `deleteDuplicateRowAndChildren()` with a recursive post-order DFS traversal:

```typescript
async function deleteRecursive(
  client: Client,
  schema: string,
  table: string,
  pkColumn: string,
  rowId: unknown,
  visited: Set<string>,
): Promise<void> {
  const tableKey = `${schema}.${table}`
  if (visited.has(tableKey)) {
    throw new Error(`Cycle detected in FK dependency graph at ${tableKey}`)
  }
  visited.add(tableKey)
  try {
    // 1. Discover all tables with FK referencing this table (pg_constraint)
    // 2. For each child table:
    //    a. Resolve child's PK via getPrimaryKeyColumn()
    //    b. Find child rows: SELECT pk FROM child WHERE fk = rowId
    //    c. Recurse into each child row (deletes grandchildren first)
    //    d. Batch-delete all direct children
    // 3. Delete the row itself
  } finally {
    visited.delete(tableKey) // allow same table in different branches
  }
}
```

### 52.2 Algorithm Properties

- **Arbitrary depth:** Post-order DFS ensures deepest dependencies are deleted first
- **Cycle protection:** `visited` set tracks current recursion path (not global). Removed on exit (try/finally) to allow same table in different branches (diamond dependency)
- **Scope safety:** Every DELETE is scoped to the specific row being reconciled via FK column = rowId
- **Transaction semantics:** Errors propagate to caller which does ROLLBACK. No try/catch swallowing
- **No hardcoded tables:** Discovers dependencies from `pg_constraint` catalog at runtime

### 52.3 Deletion Order

```
identities → customers → customer_ownership_history
```

Recursive traversal:
1. Enter identities (visited: {identities})
2. Find customers.identity_id → identities.id
3. Enter customers (visited: {identities, customers})
4. Find customer_ownership_history.customer_id → customers.id
5. Enter customer_ownership_history (visited: {identities, customers, customer_ownership_history})
6. No FK references → delete customer_ownership_history WHERE customer_id = X
7. Exit customer_ownership_history (visited: {identities, customers})
8. Delete customers WHERE identity_id = Y
9. Exit customers (visited: {identities})
10. Delete identities WHERE id = Z

**Before:** 1 pending conflict (SQLSTATE 23503 — `fk_public_customer_ownership_history_ibtob9`)
**After:** 0 pending conflicts

The exact production conflict (local identity `5f295984` vs remote `21d38960`, with customer + customer_ownership_history) was resolved by the recursive traversal. ## 53. RendererUpdater Asset Path Fix — Blank Screen Root Cause

### 53.1 Problem

After installation, the desktop app displayed a **blank blue screen**. The HTML shell loaded at `ahram://app/store/` but React never mounted (`<div id="app"></div>` was empty).

### 53.2 Root Cause

`RendererUpdater.ts` stored downloaded renderer assets **flat** at `cacheDir/filename` (e.g., `f9cc913/index-CSaPAPgD.js`).

But the bundled `index.html` references assets via the `/store/assets/` prefix:
```html
<script type="module" src="/store/assets/index-CSaPAPgD.js"></script>
<link rel="stylesheet" href="/store/assets/index-CMEwRIui.css">
```

The protocol handler strips `/store` and looks for `cacheDir/assets/index-CSaPAPgD.js` — **file not found** (it was at root). Falls back to bundled `dist/assets/` which has **different hash filenames** (e.g., `index-Cp35VhwJ.js`). Result: zero JS loads, React never mounts.

### 53.3 Fix

**RendererUpdater.ts line 85-86** — assets now stored under `assets/` subdirectory:

```typescript
// BEFORE (broken):
const filePath = join(targetDir, filename)
const dir = join(targetDir, ...filename.split('/').slice(0, -1))

// AFTER (fixed):
const filePath = join(targetDir, 'assets', filename)
const dir = join(targetDir, 'assets', ...filename.split('/').slice(0, -1))
```

**Cache repair script** — moved existing cached assets from root to `assets/` subdirectory.
